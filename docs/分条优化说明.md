# 分条（拆条）模块优化说明

分支：`feat/segment-index-splitting`（基于 main `a9c53e2`，暂不合并）

## 一、为什么改：旧方案的质量瓶颈

旧契约要求 LLM 逐字复写 8–24 字的 `anchor` 原文片段，框架再按 anchor 在原文中定位切点、切片回填。这个设计保证了「body 永远是原文切片」（方向正确，予以保留），但有一个致命短板：

**anchor 复写本身就是弱模型的能力短板。** 业界实测（High-Fidelity Information Extraction with Black Box LLMs, arXiv:2510.00276）显示，即使最强模型，引文精确匹配的失败率也有 5–10%；小模型、推理模型在长上下文里逐字复写中文时漏字、改标点、简写更是常态。而旧框架里 anchor 一旦贴不回，提议就被**静默丢弃**——没有重试、没有反馈、没有兜底，分条质量直接取决于模型复写能力。

## 二、业界参考方案

| 方案 | 来源 | 本项目采用点 |
|---|---|---|
| 行号标注法（给每行加编号，模型引用编号而非复写原文） | TDCommons *A Method for Line Number Referencing in LLMs*；*Why Your AI Code Reviewer Hallucinates Line Numbers* | **核心**：正文按段编号 `[nnn]`，模型输出起止段号 |
| 文本锚定（quote → 精确匹配 → 模糊匹配定位 span） | LangExtract 锚定机制；TACL *A Unifying Scheme for Extractive Content Selection* | anchor 降级为校验字段 + 段级模糊匹配兜底 |
| 校验失败 → 错误回喂重试 | Instructor 库（python.useinstructor.com）reask_validation 模式 | 解析/调用失败自动带错误重试 |
| 约束解码 / JSON mode | OpenAI Structured Outputs；注意「语法合法 ≠ 内容正确」需两层校验 | 可选 `response_format=json_object`，4xx 自动回退 |
| Agentic chunking（LLM 提议边界 + 框架验证） | Atlan / IBM agentic chunking；arXiv TopoChunker | 延续「模型只提议、框架裁决」的既有架构 |

## 三、新契约：段号索引制

```
章节正文 ──segment_text()──▶ 语义段序列（全局段号 0..n，UTF-8 边界安全）
        ──pack_pieces()──▶ ≤3200 字分片（每行 [nnn] 前缀，相邻分片重叠 1 段）
        ──LLM──▶ {"entries":[{"title","aliases","entity_type","start":1,"end":3}]}
        ──materialize_entries()──▶ 段号→字符偏移（确定性映射）→ body=原文切片
```

关键性质：

1. **定位与模型复写能力完全解耦**——段号 `1` 就是第 2 段的起点，不存在「写错一个字就定位失败」。
2. **body 仍然 100% 来自原文切片**——模型只给边界，不给正文，反幻觉不变。
3. **两侧共用同一 `segment_text()`**——llm.rs 编号与 split.rs 回映是同一个确定性函数，坐标系天然一致。
4. 超长段（>500 字）按句读（。！？；）自动细分，保证切点粒度。

## 四、五层防线（框架约束兜住模型下限）

`materialize_entries` 对每条提议依次尝试：

1. **段号路径**（首选）：`start` 有效 → 直接映射偏移；anchor 若能在条目开头 200 字窗口内精确命中则贴齐微调。
2. **anchor / title / 正文前缀精确匹配**（旧契约兼容，缓存旧数据仍可用）。
3. **段级模糊匹配兜底**：字符二元组 Dice 相似度 ≥0.7，应对漏字/多字/标点差异。
4. **启发式切块回退**：全部提议定位失败 → 规则切块，条目不丢失。
5. **警告透出**：回退与失败写入 `ImportReport.warnings`，导入完成后在界面上可见（修复了旧代码 `let _ = n;` 吞警告的问题）。

另有两项合并约束：

- **跨片重复提议合并**：切点相距 <24 字（一个 anchor 的约定长度）视为分片重叠区对同一条目的重复提议，别名并入前者。
- **微小条目合并**：沿用 `<24` 字无名条目并入前一条。

## 五、调用与解析加固（llm.rs）

- **错误回喂重试**（默认 1 次重试，`retries` 可配）：解析失败或调用失败时，把上次错误附在重试 prompt 里：「你上一次的输出无法使用（第1次输出解析失败：…）。请严格按系统约定重新输出」。失败结果**绝不写缓存**。
- **JSON mode 自动回退**：`json_mode=true` 时请求 `response_format=json_object`；服务端返回 4xx（代理/模型不支持）自动去掉重发，重试轮次不再浪费这次探测。
- **解析三层容错**：裸数组 → `{"entries":[…]}` 对象包装 → 从混杂文本截取 `[..]`；段号字段容忍 `"7"`、`"[003]"`、`"段7"` 等字符串形态（解不出来按「未提供」处理，不让整个数组报废）。
- **prompt 加 few-shot 示例**，并明确「条目按顺序衔接、除前言外覆盖全部正文、不跳段不重叠」。
- **缓存键 v3**：`sha1("v3|" + sha1(SYSTEM) + model + title + piece)`——prompt 一改缓存自动失效，不再手工 bump 版本号。

## 六、配置项（llmconfig.toml）

| 键 | 默认 | 说明 |
|---|---|---|
| `max_tokens` | 2048 | 单次输出上限 |
| `temperature` | 0.1 | 拆条要稳定，勿调高 |
| `retries` | 1 | 失败追加重试次数（带错误回喂），0 = 一次定生死 |
| `json_mode` | false | 请求 JSON 输出模式，代理不支持会自动回退 |

桌面端设置读写（`save_app_config`）已同步这些键。

## 七、质量验收（tests/split_quality.rs）

「框架约束兜住模型下限」的三档模型回归：

- **GoodModel**（段号精确）→ 4 条干净条目，正文衔接覆盖率 ≥95%，无警告；
- **SloppyModel**（title/anchor 全是编造，但段号正确）→ 段号路径全部救回，body 仍是原文切片；
- **HopelessModel**（段号越界、anchor/title 都定位不了）→ 回退启发式切块，警告透出到 notes。

另有单测覆盖：段号编号/超长行切分、分片重叠与全局段号连续性、跨片重复合并、模糊匹配救回错写 anchor、三种 JSON 形态解析、`refine_drafts` 全链路（llm_split.rs）。

## 八、补充修复：导语条前并（merge_leadin_drafts）

实测（罪业之潮-6k.docx）暴露的另一类碎片：**一句话导语被切成独立条目**——
「温度分层」（27 字，以"："结尾）、「取暖规则」（29 字，"以下是核心规则："）、「结算步骤：」（15 字），
完整解释都在下一条里，用户搜到光秃秃一句导语等于没查到。

修复：`refine_drafts` 末尾统一后处理（规则路径与 LLM 路径都生效）——

- 判定导语条：正文 <80 字，且正文或标题以 `：`/`:` 结尾；
- 并入**同章节前缀**的下一条：body 前置、原标题转为别名（检索「温度分层」仍可命中）；
- 重算 content_hash / alt_anchor，ordinals 重新连续编号（阅读页按 ordinal±1 找上下文，不能留空洞）；
- 完整短条目（句号结尾，如「终燃城」85 字简介）不受影响；不跨章节合并。

已知边界：Word 源文件里把「2. 应用修正」这类编号列表行做成真实标题样式时，规则层仍会按标题分块，
这属于源文档样式问题，本修复不强行猜测（强行拒绝编号标题会误伤真用编号做章节名的模组）。

## 九、已知局限与后续方向

1. 分片重叠只解决「条目跨片被看见」，若模型在两片上对同一条目给出相距 >24 字的切点，仍可能出重条（后续可加条目级语义去重）。
2. 未做条目跨文档去重（与本次范围无关）。
3. 可选的两遍式（先列标题清单、再逐个定位）未实现——段号制下单遍已稳，如后续用更弱模型可再考虑。
4. 设计文档 M3 的「切块手动合并/拆分」仍是有益补充：段号制让切点稳定后，人工修正的 `chunk_corrections` 命中率会随之提高（stable_key 按 `parent_path|title` 不变）。

## 十、给使用者的两条实操建议

1. **拆条换便宜的非推理小模型**（如 gpt-4o-mini 级）：段号制下小模型已能稳定工作；grok-4.6 这类推理模型徒增十分钟导入时间。
2. 若代理/模型支持 JSON mode，开 `json_mode = true` 可进一步降低解析失败率；不确定就先关着，重试机制已能兜底。
