## 0. 一页摘要

开席时 DM 要根据玩家口语，从「官方模组 + 私设」里立刻翻出完整条目并复制出去。现有 World Anvil / Kanka / LegendKeeper / Obsidian 解决的是「把世界写清楚」，不是「对着玩家原话 5 秒内命中并复制」。

**产品形态：** 本地优先、托盘常驻、全局热键唤出的检索面板。  
**技术形态：** Tauri 2 外壳 + Rust 检索引擎 + SQLite 战役库（运行时 WAL，对外导出为单文件快照）。  
**检索形态：** FTS5 词法检索为默认路径（**长口语先抽词**），小型中文 embedding 为可关闭的语义层，RRF 融合。  
**跨端形态：** 业务全部进 `table-canon-core`；Windows 与 Android 共用同一份 **checkpoint 后的 `.tcs` 快照**。

核心 KPI：

| KPI | 验收口径 |
|---|---|
| 模糊查询 | 别名、错字、拼音、口语释义可命中 |
| ≤ 5 秒 | 从确认查询到首屏结果；热查询 P95 ≤ 1.5 s |
| 可复制且完整 | 返回完整条目卡片，一键复制公开版 / 全文 / 来源 |

M1 无模型时，「模糊」只覆盖 **共享词 / 别名 / 拼音** 的长口语，不覆盖纯释义改写。评测必须分 `lexical` / `semantic` 两套 Recall，不得混算。

## 1. 目标与非目标

### 1.1 目标

1. 导入 DM 现有的 Word、PDF（文本层）、Markdown、TXT、RTF、HTML，尽量不强迫重写成模板。
2. 玩家用口语、别名、错别字、拼音、释义查询时，5 秒内返回完整可复制的设定条目。
3. Windows 提供桌边常驻：全局热键、置顶、不抢焦点、单实例。
4. 结果可一键复制为「玩家可见 / 全文 / 来源路径」，秘密字段可剥离。
5. 数据本地优先，默认不出网。
6. Windows 与 Android 共用同一套检索引擎和数据库文件格式。
7. 用户在卡片上改过的类型、可见性、别名，在源文件小改后重导入时必须还在。

### 1.2 非目标（第一版写死）

- 地图编辑、战斗轮次、角色卡、玩家门户、会话排期。
- 强制把资料改成 NPC / 地点表单。
- MVP 不做扫描件 OCR。
- 不做模组分享市场、云端实时同步、账号体系。
- 不以大模型改写替代原文。若后期加「用自己的话回答」，必须附原文卡片，且不得替换检索结果。
- 不要求用户手动拷贝 `.tcs-wal` / `.tcs-shm`。

### 1.3 成功标准（给评审的一句话）

选一个正在跑的中文战役文件夹 → 导入 → `Ctrl+Shift+F` → 粘贴玩家刚说的话 → 5 秒内出现完整卡片 → 一键把公开信息复制到剪贴板。这条闭环不通，产品不成立。

M1 闭环评测的长口语必须含专名或别名（lexical）。纯释义、无共享词的句子标为 semantic，不计入 M1 是否过关。

```
│  输入、卡片、快捷键、剪贴板、进度条            │
└────────────────────┬─────────────────────────┘
                     │ Tauri Command / IPC
                     ▼
┌──────────────────────────────────────────────┐
│  Rust crate: table-canon-core                │
│                                              │
│  ingest   解析 / 切块 / 别名 / 拼音 / 回套修正 │
│  search   抽词 / 规范化 / FTS / 向量 / RRF    │
│  copy     可见性过滤 / 模板渲染               │
│  db       schema / WAL / Backup 快照导出      │
│  embed    ONNX / 预热 / 超时降级 / 子块向量    │
└────────────────────┬─────────────────────────┘
                     │
                     ▼
              运行中：campaign.tcs + WAL/SHM
              导出/传手机：VACUUM INTO 得到的单文件快照
              ├── chunks + FTS5（search_text 真列）
              ├── embedding_chunks
              ├── chunk_corrections
              ├── aliases / synonyms
              └── embedding_meta
```

### 2.1 不可违反的原则

1. **查询路径绝不解析 Word / PDF。** 导入时切块建索引；查询只读 SQLite。
2. **文档 embedding 只在导入或该展示块正文变更时计算。** 查询 embedding 只编码用户当下那一句（加 BGE 查询前缀）。
3. **全部跨端业务放在 Rust core。** UI 不得实现检索、切块、可见性过滤、抽词、checkpoint。
4. **FTS 必须可单独工作。** 模型加载失败、模型 ID 不匹配、用户关闭语义时，关键词 / 拼音检索仍可用。
5. **Windows 上建库，Android 上默认只查询。** 手机不做首次全量导入。
6. **长口语禁止整句原样送进 FTS MATCH。** 必须先抽 terms（见 6.3.1）。无模型时这条仍成立。
7. **用户修正与正文分离。** `update_chunk_meta` 写 `chunk_corrections`；替换路径先删旧 chunks、后插新 chunks（避开 ordinal 撞键），但**绝不删 corrections 行**——corrections 不得有任何指向 `chunks.id` 的外键。
8. **对用户承诺的「单文件」是导出快照，不是运行中的 WAL 主库。** 传手机只走 `export_snapshot`。

## 3. 技术选型

| 层 | 选择 | 理由 | 不选 |
|---|---|---|---|
| 外壳 | Tauri 2 | 安装包小、内存低；v2 有 Android target | Electron（常驻内存高） |
| 前端 | React + TypeScript + Vite | 与 Tauri 生态匹配，Windows / Android WebView 可复用布局 | 纯原生 WinUI（安卓要重写） |
| 核心 | Rust | 检索、解析、ONNX、SQLite 同一语言；FFI 友好 | 把检索放进 Node |
| 文档解析 | `docx` crate / 纯文本；PDF 主用文本层抽取，缺 CMap 出乱码时备选 `pdfium-render` | 本地、不依赖本机 Office | COM 调 Word |
| 数据库 | SQLite 3；运行时 WAL；导出 Backup / `VACUUM INTO` | 运行快；对外仍是单文件 | 让用户手拷三文件 |
| 全文检索 | FTS5 `trigram` + 摄入期拼音展开 + **查询期抽词** | 无额外 native tokenizer，跨端一致 | 运行时依赖 `simple` 扩展（可作为 Windows 增强，非必须） |
| 中文分词（查询侧，可选） | `jieba-rs`，失败则 n-gram 兜底 | 长口语抽词 | 把整句当一个 term |
| 语义检索 | `bge-small-zh-v1.5` → ONNX，CPU | 中文小模型，查询侧几十到几百毫秒 | 默认 `bge-m3` |
| 推理 | ONNX Runtime CPU | Windows / Android 同一模型文件 | 查询路径走 Python |
| 向量召回 | 对 `embedding_chunks` 暴力 KNN | 战役规模足够 | MVP 不引入 sqlite-vec |
| 文件监听 | `notify` | 增量导入 | 轮询 |
| 全局热键 | `tauri-plugin-global-shortcut` | 桌边唤起 | 全局钩子自写 |
| 单实例 | `tauri-plugin-single-instance` | 第二次启动只唤出已有窗口 | 多进程抢热键 |

选型约束：任何会破坏「同一快照 `.tcs` 在两端打开」的库，不得进入 core。

## 4. 数据库文件格式

### 4.1 文件约定与 WAL 策略

- 扩展名：`.tcs`（Table Canon Store）
- 本质：标准 SQLite 3 文件
- `PRAGMA application_id = 0x54435331`（ASCII `TCS1`）
- `PRAGMA user_version`：schema 整数版本，从 **`2`** 起（v1.1 起含 `chunk_corrections` / `embedding_chunks` / `search_text`）
- 运行中：`PRAGMA journal_mode = WAL`
- `PRAGMA foreign_keys = ON`
- `PRAGMA busy_timeout = 5000`

打开文件时校验 `application_id`。不匹配则拒绝，并提示「不是席间索库文件」。  
`user_version` 低于当前则走迁移；高于当前则只读打开并警告。

**WAL 与「单文件」的合同（P1，必须实现）：**

| 场景 | 磁盘实际 | 对用户怎么说 |
|---|---|---|
| 本机打开、编辑、检索 | `campaign.tcs` + `campaign.tcs-wal` + `campaign.tcs-shm` | 「战役库」；不要用手去拷这些文件 |
| 关闭库 | 写事务结束后 `PRAGMA wal_checkpoint(TRUNCATE)`，再关连接 | 关闭后尽量收成单文件，不保证若崩溃残留 WAL |
| 复制到手机 / 网盘 / 分享 | **只允许** `export_snapshot(target)` | 按钮文案：「复制到手机」「导出便携库」 |
| `export_snapshot` | SQLite Backup API 或 `VACUUM INTO 'target.tcs'`；**末尾显式打开目标执行 `PRAGMA journal_mode=DELETE` 并断言成功** | 产出一致单文件快照；不含 WAL/SHM；目标 `journal_mode` 必为 `delete` |
| 用户在资源管理器只拖走 `.tcs` | 不阻止 OS，但打开时若检测到旁路 WAL 缺失则警告 | 帮助写明：可能丢最近未 checkpoint 的写入 |

禁止把「请同时拷贝三个文件」写进用户流程。那不可验收。

`close_store()` 顺序：

1. 取消进行中的导入 job（或等当前文件事务结束）
2. 所有写事务结束
3. `PRAGMA wal_checkpoint(TRUNCATE)`，**读取返回的 busy/log/checkpointed 行**；`busy != 0` 则返回错误，不假装已可拷贝
4. 关闭连接

打开已有库时：若同目录存在 `-wal`/`-shm`，按 SQLite 正常恢复；不要删除它们。

### 4.2 核心表

```sql
CREATE TABLE schema_meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

CREATE TABLE campaigns (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE source_documents (
  id            INTEGER PRIMARY KEY,
  campaign_id   INTEGER NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
  file_path     TEXT NOT NULL,
  file_name     TEXT NOT NULL,
  file_type     TEXT NOT NULL,
  content_hash  TEXT NOT NULL,
  source_rank   INTEGER NOT NULL DEFAULT 100,
  indexed_at    TEXT,
  UNIQUE(campaign_id, file_path)
);

CREATE TABLE chunks (
  id                  INTEGER PRIMARY KEY,
  campaign_id         INTEGER NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
  source_document_id  INTEGER NOT NULL REFERENCES source_documents(id) ON DELETE CASCADE,
  stable_key          TEXT NOT NULL,
  ordinal             INTEGER NOT NULL,
  entity_type         TEXT NOT NULL DEFAULT 'other',
  title               TEXT NOT NULL,
  body                TEXT NOT NULL,
  body_markdown       TEXT,
  parent_path         TEXT,
  visibility          INTEGER NOT NULL DEFAULT 1,
  aliases_json        TEXT NOT NULL DEFAULT '[]',
  tags_json           TEXT NOT NULL DEFAULT '[]',
  search_text         TEXT NOT NULL,
  source_rank         INTEGER NOT NULL DEFAULT 100,
  content_hash        TEXT,
  created_at          TEXT NOT NULL,
  updated_at          TEXT NOT NULL,
  UNIQUE(source_document_id, ordinal)
);

CREATE INDEX idx_chunks_campaign ON chunks(campaign_id);
CREATE INDEX idx_chunks_source   ON chunks(source_document_id);
CREATE INDEX idx_chunks_type     ON chunks(campaign_id, entity_type);
CREATE INDEX idx_chunks_stable   ON chunks(source_document_id, stable_key);

-- 用户手改；重导入不得删除本表行（除非源文档被用户明确移出战役）
CREATE TABLE chunk_corrections (
  id                  INTEGER PRIMARY KEY,
  campaign_id         INTEGER NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
  source_document_id  INTEGER NOT NULL REFERENCES source_documents(id) ON DELETE CASCADE,
  stable_key          TEXT NOT NULL,
  alt_anchor          TEXT,
  entity_type         TEXT,
  visibility          INTEGER,
  aliases_json        TEXT,
  tags_json           TEXT,
  updated_at          TEXT NOT NULL,
  UNIQUE(source_document_id, stable_key)
);

CREATE INDEX idx_corrections_anchor
  ON chunk_corrections(source_document_id, alt_anchor);

-- 语义检索专用子块；展示与复制仍用 chunks
CREATE TABLE embedding_chunks (
  id           INTEGER PRIMARY KEY,
  campaign_id  INTEGER NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
  chunk_id     INTEGER NOT NULL REFERENCES chunks(id) ON DELETE CASCADE,
  seq          INTEGER NOT NULL,
  body         TEXT NOT NULL,
  embedding    BLOB NOT NULL,
  UNIQUE(chunk_id, seq)
);

CREATE INDEX idx_embedding_chunks_chunk ON embedding_chunks(chunk_id);
CREATE INDEX idx_embedding_chunks_camp  ON embedding_chunks(campaign_id);

CREATE TABLE synonyms (
  id              INTEGER PRIMARY KEY,
  campaign_id     INTEGER NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
  term            TEXT NOT NULL,
  canonical       TEXT NOT NULL,
  target_chunk_id INTEGER REFERENCES chunks(id) ON DELETE SET NULL,
  created_at      TEXT NOT NULL,
  UNIQUE(campaign_id, term)
);

CREATE TABLE embedding_meta (
  id             INTEGER PRIMARY KEY CHECK (id = 1),
  model_id       TEXT NOT NULL,
  model_version  TEXT NOT NULL,
  dim            INTEGER NOT NULL,
  quant          TEXT NOT NULL,
  runtime        TEXT NOT NULL DEFAULT 'onnx',
  pooling        TEXT NOT NULL DEFAULT 'cls',
  query_prefix   TEXT NOT NULL
);

CREATE TABLE query_log (
  id           INTEGER PRIMARY KEY,
  campaign_id  INTEGER NOT NULL,
  query        TEXT NOT NULL,
  latency_ms   INTEGER NOT NULL,
  used_semantic INTEGER NOT NULL,
  created_at   TEXT NOT NULL
);

-- query_log 保留策略：每 campaign 最多 500 条，写入前删最旧（见 11.3）

CREATE TABLE copy_templates (
  id           INTEGER PRIMARY KEY,
  campaign_id  INTEGER NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
  key          TEXT NOT NULL,          -- 'player' | 'full' | 'source'
  body         TEXT NOT NULL,          -- 含 {entity_type} {title} {body} {public_body} {source_path} 占位符
  updated_at   TEXT NOT NULL,
  UNIQUE(campaign_id, key)
);

CREATE VIRTUAL TABLE chunk_fts USING fts5(
  title,
  search_text,
  content='chunks',
  content_rowid='id',
  tokenize='trigram'
);

CREATE TRIGGER chunks_ai AFTER INSERT ON chunks BEGIN
  INSERT INTO chunk_fts(rowid, title, search_text)
  VALUES (new.id, new.title, new.search_text);
END;

CREATE TRIGGER chunks_ad AFTER DELETE ON chunks BEGIN
  INSERT INTO chunk_fts(chunk_fts, rowid, title, search_text)
  VALUES ('delete', old.id, old.title, old.search_text);
END;

CREATE TRIGGER chunks_au AFTER UPDATE ON chunks BEGIN
  INSERT INTO chunk_fts(chunk_fts, rowid, title, search_text)
  VALUES ('delete', old.id, old.title, old.search_text);
  INSERT INTO chunk_fts(rowid, title, search_text)
  VALUES (new.id, new.title, new.search_text);
END;
```

`schema_meta` 至少写入：`app = table-canon`、`format = tcs`。

**应用级 vs 战役级存储分界（P1，定死）：**

- 进 `.tcs`（随战役走，跨端一致）：`copy_templates`、`synonyms`、`chunk_corrections`、`embedding_meta`。
- 独立 config 文件（不进库，不随战役迁移）：热键、窗口模式、语义开关、模型路径、最近库列表、主题。放应用数据目录（如 `%APPDATA%\table-canon\config.toml`）。

理由：热键、模型路径是「这台机器 / 这个安装」的属性，不是战役数据；混进库会导致 A 机器打开库后继承 B 机器的热键和模型路径。`schema_meta` 只放库自身属性，不放应用偏好。

`chunks` **没有** `embedding` 列。向量只存在 `embedding_chunks`。语义关闭或尚未向量化的战役，`embedding_chunks` 可以为空。

`embedding_meta.query_prefix` 写入实际使用的中文前缀，打开库时与运行时常量比对；不一致则禁用语义。

### 4.3 字段说明

**`visibility` 位标记**

| 位 | 值 | 含义 | 复制给玩家 |
|---|---|---|---|
| PUBLIC | 1 | 公开正文 | 包含 |
| DM_ONLY | 2 | DM 备注 | 剔除 |
| SECRET | 4 | 密谋 / 反转 | 剔除 |
| HIDDEN_FROM_PLAYER | 8 | 明确对玩家隐藏 | 剔除 |

默认 `PUBLIC = 1`。一块正文可同时带 `PUBLIC | SECRET`：渲染时按段切分，复制公开版只留公开段。MVP 若切段成本高，允许整块标记；M2 再做段级标记。

**`source_rank`**

数值越小优先级越高。建议约定：

- 私设 / 会话补丁：`10`
- 模组正文：`100`
- 参考资料：`200`

融合排序：先按 RRF 分，同分再按 `source_rank` 升序，再按标题。同一实体多来源时，私设覆盖官方出现在前，但官方原文仍可展开。

**`search_text`**

`chunks` 的真列，FTS 外挂 content 表依赖它。构造规则见 6.2。重导入时按新正文重算，但 aliases 以 corrections 覆盖后的集合为准。

**`stable_key` / `alt_anchor`（P0）**

用于把用户修正绑回「同一条目」，而不是绑到会随错字变化的 `content_hash`。

```
stable_key = hex(sha1(
  normalize(parent_path) + '|' +
  normalize(title)
))
# 同一文档出现相同 parent_path+title 时，再追加 '|' + ordinal

alt_anchor = hex(sha1(
  normalize(parent_path) + '|' +
  first_80_chars(normalize(body))
))
```

`normalize`：简体、半角、压缩空白、去首尾空白。  
默认不含 ordinal，避免文首插入一节导致后续全部失联。仅当同一文档出现相同 `parent_path + title` 时追加 ordinal 消歧。标题被用户改了导致 `stable_key` 失联时，用 `alt_anchor` 兜一次。两个都没命中则该条修正挂起，不静默丢弃（见 5.8）。

**`embedding` BLOB（仅 `embedding_chunks`）**

- little-endian `f32` 数组，长度 = `embedding_meta.dim`（512）
- 写入前 L2 normalize
- 打开库时若 `embedding_meta.model_id` / `pooling` / `query_prefix` 与当前运行时不一致：禁用语义层，不尝试混算

### 4.4 规模估算

| 项目 | 中型战役（估） |
|---|---|
| 文档 | 50 |
| 展示 chunk | 1–3 万 |
| embedding 子块 | 展示块的 1–3 倍 |
| 正文 | 20–80 MB |
| 512 维 f32 向量 | 若 6 万子块 ≈ 120 MB |
| FTS 索引 | 与 search_text 同量级 |
| 单文件快照合计 | 通常 < 400 MB |

多音字全读音展开（6.2）会让 `search_text` 比「单读音」再膨胀一档，但仍是文本级冗余，量级不跳档；上表「< 400 MB」已含此膨胀。若实测逼近上限，可在 4.4 复核时评估「仅展开首字母串全组合、全拼只保留最常见读音」的降级，但 M1 不引入该折中。

6 万向量暴力点积：Rust 单线程数十毫秒量级，不必上 ANN。超过 10 万 embedding 子块再评估 sqlite-vec / HNSW，不进入 MVP。

## 5. 文档摄入

### 5.1 支持格式

| 格式 | MVP | 说明 |
|---|---|---|
| `.docx` | 是 | OOXML；标题样式 + 段落 + 表格 |
| `.md` / `.txt` | 是 | |
| `.html` | 是 | 去标签留文本与标题 |
| `.rtf` | 是 | 尽力转纯文本 |
| `.pdf` | 是，仅文本层 | 无文本层则标记「无法提取」，不计入失败导入的整体中断 |
| 扫描 PDF / 图片 | 否 | 明确不做 OCR |
| `.doc`（老二进制） | 否 | 提示另存为 docx |

**txt 编码探测（P1）：** 国内 DM 的老 txt 大量是 GBK / GB18030。读 txt 一律走 `encoding_rs`：先按 UTF-8 解码，遇到无效序列回退 GB18030（GB18030 是 GBK 超集，一并覆盖）。`.md` 按 UTF-8 处理（标准如此），解码失败也回退 GB18030 并给出「已按 GBK 识别」提示。禁止 `String::from_utf8` 直接 panic。

### 5.2 流程（含修正回套）

```
选文件或文件夹
  → 文档身份：战役相对路径（相对本次导入根，统一 `/`），写入 source_documents.file_path
  → 计算 SHA-256(content)（真 SHA-256，禁止用 SHA-1 顶名）
  → 先按 (campaign_id, file_path) 查找
      命中且 hash 相同则跳过
      命中且 hash 不同则进入「替换该文档」事务（见下），不得先 DELETE corrections
      未命中则按 (campaign_id, content_hash) 查找：恰好一条视为重命名，更新 file_path 后按 hash 是否变化决定跳过或替换
  → 导入根目录下的非文档扩展名（图片/二进制）静默跳过；`.pdf`/`.doc` 记入报告但不中断整次导入
  → 解析为 Block[]（heading_level, text, style, table_rows）
  → 切展示块（200–2000 字）
  → 为每块生成 stable_key、alt_anchor、ordinal
  → 规则识别 entity_type / aliases / visibility
  → 按 (source_document_id, stable_key) 再按 alt_anchor 回套 chunk_corrections
  → 用回套后的 aliases 生成 search_text（含拼音）
  → 快照旧块向量（(stable_key, content_hash) → 该块的 embedding 子块）
  → 删除该文档旧 chunks（FK 级联删旧 embedding_chunks；corrections 保留）
  → 写入新 chunks
  → 复用未变块的旧向量，只重算真改块（见 5.2.1）
  → 更新 indexed_at
```

**替换事务顺序（P0，写死）：**

1. 读取该 `source_document_id` 的全部 `chunk_corrections` 到内存。
2. 解析并生成 **新** chunk 候选（含 ordinal，从 0 起）。
3. 匹配 corrections → 覆盖候选上的 `entity_type` / `visibility` / `aliases_json` / `tags_json`。
4. 快照旧块向量：`Map<(stable_key, content_hash) → Vec<embedding 子块>>`（见 5.2.1）。
5. DELETE 旧 chunks（`ON DELETE CASCADE` 清旧 `embedding_chunks`；corrections 不挂 chunk id，不受影响）。
6. INSERT 新 chunks。**必须先删后插**：`chunks` 有 `UNIQUE(source_document_id, ordinal)`，新旧块同文档、同 ordinal 从 0 起，先插必撞键回滚。
7. 复用快照向量：新块 `(stable_key, content_hash)` 命中旧快照则直接搬回；未命中才 encode（5.2.1）。
8. 未匹配上的 corrections **保留**，`stable_key` 不变，供下次标题/顺序再对齐；在导入报告列出「N 条修正未挂上新块」。
9. 提交。失败则整文件回滚，旧块与修正都在。

**硬约束（替代 v1.1「禁止先删后插」的旧表述）：**

- `chunk_corrections` 的 FK 只挂 `source_documents` 与 `campaigns`，**不得有任何指向 `chunks.id` 的外键**。这是「先删后插」不伤修正的前提。
- 替换路径**不得 DELETE 任何 `chunk_corrections` 行**（除非该源文档被用户明确移出战役，走 5.7）。
- 只要这条 FK 约束成立，先 DELETE 旧 chunks 就动不到 corrections；v1.1 担心的「级联清掉手改」在此 schema 下不成立。

要求：

- 进度：`已处理 12/40 文件，当前：港口篇.docx`
- 可取消；取消时回滚当前文件事务，已完成文件保留
- 导入在后台线程；检索界面不阻塞
- 开席过程中只允许增量，禁止全库重建

### 5.2.1 重导入的向量复用（P2）

「改一个错字」不应重算整档向量。替换前先对旧 `embedding_chunks` 建快照：

```
旧块 → key = (stable_key, content_hash)
       val = 该 chunk 的所有 embedding 子块（按 seq 排序）
```

替换后对新块逐个判断：

| 新块状态 | 处理 |
|---|---|
| `(stable_key, content_hash)` 命中快照 | 旧向量原样搬回，不 encode |
| `stable_key` 命中但 `content_hash` 变 | 该块 encode |
| 全新块 | encode |

`content_hash` 必须基于**该展示块的正文文本**（不是源文件整体），否则任何小改都会让所有块 hash 变、复用失效。切块时顺带算每块正文的 hash 存 `chunks.content_hash`。

这是与「改错字不丢手改」对称的承诺：**改错字既不丢手改，也不重算全档向量**。

### 5.3 切块规则（展示块 ≠ 语义块）

展示 / 复制用的主切块，按优先级：

1. Word 样式标题（Heading 1–4）或 Markdown ATX / Setext 标题
2. 用户配置的分隔符（如 `---`、`【NPC】`）
3. 连续空行
4. 硬上限切分：单块 **200–2000 字**（按 Unicode 标量计）。超过则在句号 / 换行处切开
5. overlap **50–100 字**，避免设定写在段末、标题在下一块

每块保留：

- `title`：最近标题，无标题则取首句截断 40 字
- `parent_path`：如 `第二章 / 港口 / 断桅酒馆 / 格里姆`
- `ordinal`：文件内序号
- 来源：文件名 + 块序（PDF 能取到页码则写入 path）

表格：每行转为 `字段：值` 文本，并入所属标题块；独立属性表可成单独 chunk。

**不要**为了 BERT 的 512 token 把展示块降到 400 字。完整可复制是产品 KPI；语义窗口在 7.6 另切。

### 5.4 实体类型

`npc | location | item | faction | rule | plot | other`

规则优先于模型：

- 标题或首行含「NPC」「人物」「地点」「城镇」「物品」「魔法物品」「势力」「组织」「规则」「密谋」「线索」
- 字段名：`姓名：` `别名：` `外观：` `动机：`
- 用户在结果卡片上改类型，写入 `chunk_corrections`，并 materialize 到当前 `chunks` 行

不在 MVP 做 NER 大模型。误分类只影响筛选，不影响全文命中。

### 5.5 别名提取

正则与启发式（中文）：

- `又名[:：]\s*(.+)`
- `别名[:：]\s*(.+)`
- `亦称\s*(.+)`
- 标题后括号：`格里姆（独眼酒保）`
- 顿号 / 斜线分隔多个别名

写入 `aliases_json` 与 `search_text`。用户可在同义词表补「独眼酒保 → 格里姆」。用户在卡片上增删的别名走 corrections，重导入后与规则抽取 **合并去重**（用户删除过的别名：M2 再做 tombstone；M1 用户增的别名保留，规则新抽出的照加）。

### 5.6 可见性启发式（可关）

段落以 `【秘密】` `【DM】` `DM only` `对玩家隐藏` 开头，则该段或该块打上 `SECRET` / `DM_ONLY`。误标可手改（进 corrections）。默认宁可少标，不要把公开正文藏掉。

用户手改过 `visibility` 的块：重导入时 **以 corrections 为准**，不再被启发式覆盖。

### 5.7 增量与文件夹监视

- `notify` 监听已添加的根目录
- 事件合并：同一文件 1 秒内多次保存只索引一次
- 删除文件：询问；确认后删除 `source_documents`（级联 chunks / embedding_chunks / **该文档的 corrections**）
- 重命名：按 hash 识别同一文件，更新相对 `file_path`，corrections 跟着 `source_document_id` 走。禁止把 Windows 绝对路径当主键。

### 5.8 `update_chunk_meta` 与 corrections

IPC `update_chunk_meta` 必须：

1. UPSERT `chunk_corrections`（键：`source_document_id + stable_key`），写入非空字段；`alt_anchor` 按当前 body 刷新。
2. 同步 UPDATE 当前 `chunks` 对应行（检索立即生效，不必等重导入）。
3. 若改了 aliases，重算该行 `search_text`（触发器会更新 FTS）。
4. **不**因 meta 变更重算 embedding，除非以后把 aliases 拼进 embedding 文本（M1 不拼）。

读取路径：当前会话以 `chunks` 上已 materialize 的值为准。重导入走 5.2 回套。禁止只改 `chunks` 而不写 corrections。

## 6. 模糊检索

### 6.1 四层，由便宜到贵

| 层 | 手段 | 解决 | 默认 |
|---|---|---|---|
| L1 规范化 | **简繁默认开**（M1 静态映射，可关；后期可换 OpenCC）、全半角、空白压缩、标点 | `獨眼` = `独眼`，`ＮＰＣ` = `NPC` | 开 |
| L2 词法 | **抽词** + FTS5 trigram + 摄入拼音 + LIKE 兜底 | 子串、前缀、拼音、长口语 | 开 |
| L3 别名 | `aliases_json` + `synonyms` | 「独眼酒保」 | 开 |
| L4 语义 | 查询向量 × `embedding_chunks` + RRF | 口语对不上标题 | 开，可关 |

「模糊」不是无界生成。现场要的是可核对原文。

M1 无模型时，L4 关闭。L2 抽词仍必须做，否则粘贴整句等于没查。

### 6.2 `search_text` 构造（摄入期）

对每个 chunk 拼接后写入 `chunks.search_text`：

```
title
body
aliases 各一行（含 corrections 合并后）
同义词 canonical / term
拼音全拼（空格分词，带引号短语）
拼音连写全拼（`gelimu`，供用户不打空格）
拼音首字母串（`glm`）
规范化后的 body（简体、半角）
```

拼音用纯 Rust 库（如 `pinyin` crate）在摄入时生成。查询侧抽词后，每个 ≥3 字符的拼音 term 也送进 FTS。这样 **Android 不必编译 sqlite `simple` 扩展**。

**只展开标题和别名，禁止正文逐字读音。** 正文逐字会把 `shi` / `zhe` 写进索引，OR 查询噪声极大。专名出现在正文但不在标题/别名时，靠汉字 n-gram 命中，不靠拼音。

**多音字（P1）：** 「长/重/还/单/解/行/藏」等常见多音字，用户按另一读音输入就会 miss。标题/别名按 **全部读音** 展开（如 `cháng`/`zhǎng`），写入 search_text，查询侧同样展开。笛卡尔积上限 16 组，超出则截断（M1 可接受；超长标题优先保前缀组合）。首字母串同样展开全部组合。

例：标题/别名「格里姆」→ 索引 `ge li mu`、`gelimu`、`glm`。用户打 `gelimu` / `ge li mu` / `glm` 都能走词法。两字「格里」走 B 层 LIKE（标题子串），不走 trigram。「隐藏」会同时索引 `yin cang` / `yincang` 与 `yin zang` / `yinzang`。

### 6.3.1 查询词抽取（P0，M1 门槛）

招牌能力是粘贴玩家整句话。FTS5 trigram 对长短语整句 MATCH 极窄，**禁止** `MATCH q1`。

```
输入：q1（规范化后的玩家口语）
输出：terms[]（已转义，可进入 FTS）

1. 提取连续汉字串 run[]；连续拉丁/数字串作为专名候选直接入 terms
2. 对每个汉字 run：
   a. 长度 <= 6 且 **≥3 字**：原词入 terms；其拼音（空格全拼 / 连写 / 首字母，均须 ≥3 字符）入 terms
   b. 长度 1–2 字：**不入 A 层 terms**（trigram 匹配不了）；短查询由 B 层负责
   c. 长度 > 6：
      - 若 jieba-rs 词典可用：分词 → 去掉停用词
        → **只保留 ≥3 字片段**入 A 层；2 字词不得直接 MATCH
        → 相邻 2 字词可再拼成 ≥3 字短语后入 A
      - 若分词不可用或可用 ≥3 字片段 < 2 个：
        → 对该 run 做 **3-gram / 4-gram** 滑窗（禁止 2-gram 进 A）
        → 丢掉首字或尾字落在停用词表的候选
        → 更长的 n-gram 权更高，最多保留 32 个
3. 同义词展开：term 命中 synonyms.term 则加入 canonical，
   以及 target_chunk 的 aliases（若有）
4. 去重；转义 FTS 特殊字符；`AND/OR/NOT/NEAR` 即使是用户词也必须加引号
5. 上限 48 个 term；超出按权重截断（更长、非停用、命中 synonym 优先）
6. 仅当规范化后全文汉字数 <= 6 且 ≥3 时，才把整句本身作为一个短语 term
7. 纯拉丁输入：去掉空格后的连写串（`gelimu`）若 ≥3 字符，必须入 terms
```

M1 停用词最小表（可扩，但**不要**把「人 / 地方 / 东西」这类实词放进去，会误杀 NPC 名与地名 n-gram）。**这是运行时资源，随应用分发**（如 `crates/table-canon-core/assets/stopwords.zh.txt`），不是测试数据，不得只放 `testdata/`——正式版必须带上：

```
的 了 在 是 我 我们 他 她 他们 有 和 就 都 也 还 这 那
个 一下 一下下 之前 刚才 然后 但是 如果 因为 所以
去 到 把 被 让 给 要 想 说 问 看
```

评测用句「我们之前在那个独眼酒保的店里拿到了货」至少应抽出类似：

```
独眼酒保（4-gram，A 层）
独眼酒 / 眼酒保（3-gram，A 层）
→ 可选 synonym：独眼酒保 → 格里姆
```

**不得**把 1–2 字「独眼、酒保、店、货」当作 A 层成功标准——它们进 trigram MATCH 等于空打。无同义词时，4-gram `独眼酒保` 必须仍能命中标题/正文含该片段的块。不得把「我们之前在那个」整段当唯一 MATCH 串。

### 6.3 查询流水线

```
q0 = 原始输入（可粘贴整段玩家发言；>2000 字截断并提示）
q1 = 规范化(q0)
terms = extract_terms(q1)          # 6.3.1
terms = 同义词展开(terms)

第一遍 A1：
  FTS5 MATCH OR(terms) **ORDER BY bm25(chunk_fts)**，limit 50
  必须 JOIN chunks 过滤 campaign_id，禁止只扫 FTS 虚表
若 |A1| < 3 且存在长度 > 6 的汉字 run：
  第二遍 A2：对该 run 再放宽 3-gram/4-gram（仍受 48 term 上限；仍禁止 2-gram 进 A）
  A = A1 ∪ A2
否则：
  A = A1

B = 仅当「原始输入 q1 规范化后整体汉字数 ≤ 4」时启用：
    对 q1 做 LIKE / INSTR，只扫 title 与 aliases_json（不扫 search_text 全文），limit 30
C = 若语义开启且模型就绪：embed(query_prefix + q1) → embedding_chunks 上 top 50 KNN
    → 映射为 chunk_id；同一 chunk 多子块命中时只保留最好的一条 rank
D = RRF(A, B, C)，k = 60
E = 同一 source_document + 近似 title 去重
F = source_rank 微调
G = 取 Top 20，附 highlight 与 copy payload
```

超时：

- 语义 embed 硬超时 **800 ms**（可配），超时则丢 C，只返回词法
- 整次查询硬超时 **4500 ms** 必须出首屏
- UI 渲染预算 100 ms，20 条列表虚拟滚动

抽词本身预算 **≤ 20 ms**。jieba 若加载失败，立即走 n-gram，不得拖过这 20 ms。

### 6.4 FTS 查询构造注意

FTS5 trigram **对不足 3 个 unicode 字符的 token 不命中任何文档**。因此：

- A 层禁止 1–2 字汉字 term、禁止不足 3 字符的拼音音节
- 1–2 字短查询必须走 B 层（且 B 层只在短查询启用，见 6.3）
- 用户输入含 FTS 特殊字符或关键字（`"` `*` `AND` `OR` `NOT` `NEAR`）时要在 **每个 term** 上转义并加引号，禁止把玩家原文当原始 MATCH 语法执行
- 提供高级模式（可选）才允许用户手写 `NEAR`

**拼音短语必须整体引用（P3）：** `ge li mu` 若不加引号会被 FTS 拆成 `ge` / `li` / `mu`，各自不足 3 字符。空格全拼一律 `"ge li mu"`；连写 `gelimu` 与首字母 `glm` 是连续串，可不过滤空格。查询侧对纯拉丁输入必须同时生成连写串。

默认 MATCH 由抽词结果自动生成，对 DM 不可见。界面可显示「本次检索词：独眼、酒保、格里姆」便于排障，M1 建议做（一行灰字即可）。

### 6.5 RRF

\[
\mathrm{score}(d) = \sum_i \frac{w_i}{k + \mathrm{rank}_i(d)}
\]

- \(k = 60\)
- 默认 \(w_{\text{fts}} = 1.0\)，\(w_{\text{like}} = 0.7\)，\(w_{\text{vec}} = 1.0\)
- 未出现在某路召回中的 \(\mathrm{rank}\) 视为缺失，该项为 0
- 向量路：同一 `chunk_id` 只贡献 **一个** rank（其子块中最好的）。禁止把多个 embedding 子块的 rank 相加，避免长条目靠块数刷分

### 6.6 高亮

- FTS 命中：用 **抽出来的 terms** 在 `body` 中找偏移，前端标色
- 语义命中无词重叠时：不高亮生造词，只在卡片角标标明「语义」
- 禁止用模型改写后再高亮

## 7. Embedding

### 7.1 默认模型与导出口径（P1）

| 项 | 值 |
|---|---|
| 模型 | `BAAI/bge-small-zh-v1.5` |
| 参数量 | 约 24M |
| 输出维度 | 512 |
| max_length | 512 token |
| 发布格式 | ONNX（INT8 或 FP32，以召回评测定） |
| 体积 | FP32 约 96 MB；INT8 / Q8 约 25–30 MB |
| 推理 | ONNX Runtime，CPU，查询 batch=1 |
| 线程 | Windows 查询 2 线程；Android 1–2 线程，避免过热 |
| pooling | **CLS**（不是 mean pooling） |
| 归一化 | 向量写入前 **L2**；查询同样 L2；检索用点积 |
| 文档侧前缀 | **无** |
| 查询侧前缀 | `为这个句子生成表示以用于检索相关文章：` |
| 超长截断 | BertTokenizer，**截右侧** |

英文战役可换 MiniLM，但 **一个 `.tcs` 只允许一种 `model_id`**。换模型必须离线全量重算 `embedding_chunks`。

明确不默认：`bge-m3`、`e5-large`、任何生成式 LLM。

查询前缀与 pooling 不是可选优化。导错则语义召回整体崩，必须走 7.1.1 验收。

### 7.1.1 ONNX 导出验收（CI 必跑）

`testdata/embed_golden.json`：固定 ≥ 10 句中文。

1. 参考实现：官方 FlagEmbedding / sentence-transformers，同一模型，CLS + L2，查询句加前缀。
2. 产品 ONNX 路径对同一输入出向量。
3. 逐句余弦相似度**分量化门槛**：
   - FP32 产物：**≥ 0.999**
   - INT8 产物：**≥ 0.995**（动态量化余弦常落在 0.995–0.9998，0.999 对 INT8 是随机失败的门禁，会卡发布）
4. 任一句低于对应门槛 → 该产物不得打进安装包，语义开关保持不可用。
5. **真正的一票否决是 13.3 的 Recall@10**：golden 只防「导出写错（pooling / 前缀 / 归一）」，召回由评估集说话。golden 过、Recall 崩，同样不得发布语义。

此测试不依赖战役库，CI 每次构建语义产物都跑。

### 7.2 何时计算

| 对象 | 何时 | 查询时是否重算 |
|---|---|---|
| 每个 embedding 子块 | 导入或对应展示块 `content_hash` 变 | 否 |
| 用户查询 | 语义开启且模型已预热 | 是，只 encode `prefix + q1` |
| 换模型 | 维护操作，全量离线 | — |

相同查询文本（含前缀后的字符串）可做短时内存缓存（如 2 分钟、最多 64 条），避免 debounce 重复 encode。

### 7.3 预热与降级

- 托盘启动后异步加载 ONNX，不挡主窗
- 加载中：界面显示「语义准备中，当前仅关键词」
- 加载失败 / 内存不足：永久降级到 FTS，直到用户重试
- 查询 embedding 失败：当次降级，不视为整次查询失败
- golden 向量测试未通过的构建：等同加载失败

### 7.4 硬件口径（写入帮助页）

**Windows 查询**

- 最低：Win10/11 64 位，4 GB RAM，无 GPU
- 推荐：8 GB RAM（同时开语音、浏览器）
- 导入上百页：推荐 8 GB+、SSD

**Android 查询**

- 中端机上，同类 INT8 小模型单次 encode 通常数十毫秒，整段检索 P95 远低于 5 秒
- 模型打进包或首次下载约 25–30 MB，可接受
- **禁止在手机上做首次全量建库**
- 只保 `arm64-v8a`；32 位设备仅 FTS

### 7.5 向量检索实现

对当前战役 `embedding_chunks.embedding` 做点积 top 50，再映射 `chunk_id`。  
内存：子块向量可能到 ~120 MB + 模型 30–100 MB，查询峰值预留 300–400 MB 进程内。

不在查询路径调用 Python。

### 7.6 语义子块（P1）

BGE / BERT 上限 512 token ≈ 中文约 400–500 字。展示块上限 2000 字，若整块送模型，尾部不进向量，语义对该块半失效。

规则：

| 展示块汉字数 | `embedding_chunks` |
|---|---|
| ≤ 400 | 1 行，`body` = 展示块全文，`seq = 0` |
| > 400 | 窗口 **400 字 + 50 字重叠** 切开，`seq = 0..n-1` |

- 切窗口时尽量在句号 / 换行处断，对不齐则硬切
- 每个子块单独 encode（无查询前缀），L2 后写入
- 检索命中子块后，**结果单位永远是展示 `chunks`**：复制、展开、高亮都用完整 `body`
- RRF 向量路每个 chunk 只取最好子块 rank（见 6.5）
- 语义关闭：不写 `embedding_chunks`，查询不读该表

不得把展示块硬上限改成 400 字来迁就模型。

## 8. 性能预算

**超时口径（P3，统一）：对外承诺 5 s，内部预算 4.5 s（给渲染留 500 ms）。** 其余处写「硬超时」一律指内部 4.5 s 出首屏；对用户的文案只说「≤ 5 秒」。不得再出现两套数字。

| 阶段 | 预算 |
|---|---|
| 热键唤出 → 输入框可打字 | ≤ 100 ms（进程常驻） |
| 抽词 + L1 | ≤ 20 ms |
| L2+L3 词法 | ≤ 100 ms |
| 查询向量 | ≤ 800 ms（超时丢语义） |
| KNN + RRF + 取正文 | ≤ 100 ms |
| UI 渲染 20 条 | ≤ 100 ms |
| **热查询 P95** | **≤ 1.5 s** |
| **硬超时出首屏** | **4.5 s** |
| 冷启动首次加载模型 | 允许 > 5 s，但必须发生在预热阶段，不得发生在第一次回车 |

冷启动窗口本身：允许 1–2 s 出托盘；用户第一次按热键时，若模型未好，仍必须在 5 s 内给出 FTS 结果。

## 9. Windows 客户端

### 9.1 进程与窗口

- 单实例。第二次启动把参数交给已有进程并聚焦。

- 唤出：置顶、不强制抢其它程序的全屏独占（游戏全屏可能失败，需在帮助中说明）

### 9.2 输入

- 聚焦后可直接粘贴；检测到剪贴板多行且来自热键唤出后 300 ms 内粘贴，则自动搜


### 9.4 复制

模板存 `copy_templates` 表（随战役走，跨端一致），可改。默认三键：

```json
{
  "player": "{entity_type}　{title}\n{public_body}\n—— {source_path}",
  "full": "{title}\n{body}\n来源：{source_path}",
  "source": "{source_path}"
}
```

占位符：`{entity_type}` `{title}` `{body}` `{public_body}` `{source_path}`；由 `copy_payload` 在 core 内填充。

- `public_body` 由 core 按 visibility 过滤后给出，前端不得自己删秘密
- 支持纯文本 / Markdown 两种剪贴板格式（CF_UNICODETEXT；可选 HTML）
- 成功后 toast 1 秒，并写入「本场已用」
- 本场已用仅内存 + 可选会话表，不作为第二套百科

### 9.5 设置页（MVP 最小集）

- 战役库路径、最近库列表

- 导入根目录
- 复制模板

不做账号、云、主题市场。

### 9.6 前端约束

- 不把 chunk 原文送出本机

### 12.2 备选路径

Flutter 只写 UI，JNI / FFI 调 core。触发条件：Tauri Mobile 在目标时间点无法稳定热更新、后台、文件选择。

### 12.3 行为差异

| 能力 | Windows | Android |
|---|---|---|

| 悬浮窗 | 置顶窗口 | 不作为承诺；受系统限制 |

### 12.4 硬规则

- 库头 `model_id` / `pooling` / `query_prefix` 不一致 → 只开 FTS
- APK 只带一个 small 模型，或不带模型、首次可选下载
- 不把 Windows 绝对路径写进 core 逻辑；`file_path` 存战役相对路径，仅作展示、监视与重导入身份。迁移后若相对路径仍在则继续用；失效则显示 `file_name`
- 从 Windows 到手机的唯一受支持路径：桌面 `export_snapshot` → 用户拷贝该快照 → 手机打开
- 手机端打开的是 **`journal_mode=DELETE` 的快照**（`export_snapshot` 已保证）。Android / 验收路径必须走 `open_portable`：**不得**主动切成 WAL。若本地要写（改 meta / 导入），先在应用私有目录复制一份再 `open`（WAL），不写原快照，避免「cannot open WAL database in read-only」类坑
- 「再传回 Windows」同样必须走 `export_snapshot`（若手机端改过，先在手机导出快照）

## 13. 测试与验收

### 13.1 功能

- 导入 docx / md / txt / 文本层 pdf
- 无文本层 pdf 明确提示，不崩溃
- 标题路径、别名、拼音、1–2 字短查询
- **长口语抽词**：含专名的整句在无模型时能命中（见 13.3 lexical）
- 口语纯释义（语义开）走 semantic 集
- 复制公开版不含秘密段
- 热键唤起、Esc 隐藏、单实例
- 文件夹增量：改一个文件只重算该文件
- **改一个错字重导入后，手改的 visibility / aliases / entity_type 仍在**
- **改一个错字重导入后，未变块的 embedding 子块复用旧向量（不触发 encode）——用 encode 计数器或埋点断言只重算真改块**
- 错误库文件 / 未来版本库的拒绝与只读
- `export_snapshot` 产出单文件；用独立 SQLite 打开无 `-wal`；chunk 数与源库一致；**`PRAGMA journal_mode` 返回 `delete`**
- 关闭库后 checkpoint；失败有明确错误

### 13.2 性能

- 热查询 P95 ≤ 1.5 s（测试机：8 GB RAM、无独显或核显）
- 预热完成后首次语义查询 ≤ 5 s
- 查询过程 CPU 采样：无 docx/pdf 解析
- 200 页模组导入后台可完成；导入中仍能搜已入库内容

### 13.3 检索评估集（必须有）

`testdata/eval.jsonl`：≥ 30 条玩家口语，每条必须带：

```json
{
  "query": "我们之前在那个独眼酒保的店里拿到了货",
  "relevant_chunk_ids": ["格里姆（独眼酒保）"],
  "kind": "lexical",
  "must_extract_any": ["独眼酒保"]
}
```

M1 的 `relevant_chunk_ids` 用展示块 **title**（或其它稳定可读键），不要用会随 DELETE/INSERT 变化的整数 `chunks.id`。`must_extract_any` 至少一项必须是 **≥3 字** 的 A 层 term（或 ≥3 字符拼音）；1–2 字条目只能用于 B 层短查询用例，且该字段可为空。

`kind`：

| kind | 含义 | 计入 |
|---|---|---|
| `lexical` | 句中含专名、别名或与正文共享的 2 字以上片段 | **M1 必过**，语义开关关闭跑 |
| `semantic` | 无共享词的释义 | **M2**；M1 可跑但不作为发布门槛 |

目标（中文战役样例库）：

- `lexical` Recall@10 ≥ 0.85（语义关）
- `semantic` Recall@10 ≥ 0.70（语义开，M2）
- 私设 rank 高于同实体官方块
- 关闭语义后，纯专名 / 拼音查询 Recall@10 仍 ≥ 0.75
- 抽词：`must_extract_any` 至少命中一个，否则该用例 lexical 直接失败

评估脚本放在 core 的 integration test，CI 可跑（不含大文档）。

### 13.4 跨端

- Win10、Win11 各一
- Android 模拟器 + 至少一台中端真机
- **必须用 `export_snapshot` 生成的文件** 在两端打开，chunk 数、随机 10 条 lexical 查询的 top1 一致
- 禁止用「从正在运行的目录里只拷 `.tcs`」作为跨端测试步骤
- 语义都开且模型相同时，另测 10 条 semantic 的 top1（M2）

### 13.5 Embedding golden

见 7.1.1。语义产物构建门禁。

## 15. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| Word 结构混乱，切块垃圾 | 检索再准也是错条目 | 三种切分策略；M3 手动合并；评估集含「烂 Word」 |
| 扫描 PDF | 空库 | MVP 拒绝并说明；OCR 不进 5 秒承诺 |
| 中文 PDF 缺 CMap / 缺字体 | 文本层抽取出乱码 | 检测乱码比率；备选 `pdfium-render`；仍乱码则该 PDF 标「无法提取」 |
| trigram 短查询差 | 「酒」「塔」搜空 | LIKE / 标题前缀兜底 |
| 长口语整句 MATCH | M1 闭环假绿 | 6.3.1 抽词；lexical/semantic 分账 |
| 重导入清掉手改 | DM 拒用 | corrections 表 + 5.2 顺序 |
| 2000 字块截断进 BERT | 语义半瞎 | 展示块与 embedding 子块分离 |
| pooling / 前缀错误 | 语义全崩 | golden 余弦分层门禁（FP32 ≥0.999 / INT8 ≥0.995）+ Recall@10 一票否决 |
| 裸拷 WAL 主库 | 手机静默少数据 | 只允许 Backup 快照；帮助写死 |
| 语义拖慢或拖垮旧机 | 超过 5 s | 小模型、预热、可关、超时降级 |
| 两端模型不一致 | 乱序 / 崩溃 | `embedding_meta` 强校验 |
| Tauri Android 不成熟 | 迁移延期 | core 无 Tauri 依赖，可换 Flutter UI |
| 做成 Wiki | 范围爆炸 | 里程碑外需求一律 backlog |
| 模组版权 | 法律 | 本地索引、无市场、导出剥离秘密 |
| 全局热键与游戏冲突 | 桌边失败 | 可改键；帮助写明全屏游戏限制 |
| ONNX 运行时体积 | 安装包变大 | 运行时按平台裁剪；模型可外置 |
| jieba 词典体积 / 许可 | 安装包、法务 | 可关分词，n-gram 兜底；词典许可写入关于 |

## 16. 开放问题（请审核人拍板）

v1.1 **已关闭、不再问**的项：

- 长口语是否抽词 → **必须抽，M1 门槛**
- 手改是否独立于 chunk → **必须 `chunk_corrections`**
- 2000 字 vs 512 token → **展示块不变，语义另切子块**
- 单文件 vs WAL → **运行 WAL，对外只给快照**

v1.3 **已关闭、不再问**的项：

- 简繁默认 → **默认开，可关**
- jieba 是否挡住 M1 → **不挡；M1 无 jieba 过 lexical**
- 2 字 term 进 FTS → **禁止；A 层 ≥3 字**
- 源文件绝对路径当主键 → **禁止；相对路径 + hash 认重命名**

v1.2 **已关闭、不再问**的项：

- 替换顺序先插后删撞 UNIQUE → **先删旧 chunks 再插新 chunks**（corrections 无 chunk FK，不受伤）
- txt 编码 → **encoding_rs，UTF-8 失败回退 GB18030**
- 多音字 → **摄入 / 查询两侧展开全部读音**
- 复制模板 / 应用设置存哪 → **模板进 `copy_templates`，应用偏好进 config.toml**
- B 层全表扫 → **只短查询、只扫 title + aliases**
- 快照 journal → **强制 DELETE 并断言**
- INT8 golden → **FP32 ≥0.999 / INT8 ≥0.995，Recall@10 一票否决**
- 重导入重算向量 → **未变块复用旧向量**

仍需拍板：

1. **M1 是否必须带语义？** 建议：否。M1 过 lexical 闭环；语义进 M2。若审核要求「模糊=语义」，则 M1 就要带 ONNX + 7.1.1 + 7.6。
2. **简繁是否默认双向？** **已关闭：默认开，可关。** M1 用静态繁→简映射；查询与摄入都先 `normalize`。
3. **模型分发：** 安装包内置 INT8（约 30 MB）还是首次可选下载？
4. **Android 悬浮窗是否写进承诺？** 建议不承诺。
5. **玩家可见过滤：** 固定标记（【秘密】）还是允许自定义正则？建议 M2 固定标记 + 手动位，自定义正则进 M3。
6. **多战役跨库搜索？** 建议不做。一次只打开一个库。
7. **`.doc` 老格式：** 建议不做，提示另存 docx。
8. **是否允许高级用户手写 FTS 语法？** 建议默认关，设置里开。
9. **jieba 词典：** **已关闭：M1 无 jieba，lexical 集必须在纯 n-gram 下过线。** 若 M2 加 jieba，2 字词不得直接进 trigram MATCH，须拼成 ≥3 字或只用于 B 层。

## 18. 附录：一次查询的时序（语义开、模型已预热）

```
t=0      用户 Enter
t<20ms   规范化 + 抽词 + 同义词
t<80ms   FTS5 OR(terms) + 必要时第二遍 n-gram + 短查询 LIKE
t<200ms  ONNX encode(prefix + q1)（可与 FTS 并行；不够再并行）
t<50ms   embedding_chunks 点积 → chunk 去重 + RRF + 读 20 条展示正文
t<100ms  UI 绘制
合计     目标 < 500 ms；P95 < 1.5 s
```

若 ONNX 未就绪：跳过 encode，词法结果照出，角标「仅关键词」。抽词仍执行。

## 19. 附录：重导入与修正的最小验收剧本

1. 导入含「格里姆」的 docx。
2. 将该块标为 SECRET，别名加上「独眼酒保」。
3. 在 Word 里改一个无关错字，保存。
4. 再导入同一路径。
5. 断言：该条目仍为 SECRET，别名仍含「独眼酒保」；FTS 搜「独眼酒保」能命中。
6. `export_snapshot` 到临时路径；断言快照 `journal_mode = delete`；用另一连接打开快照；重复步骤 5。
7. 关闭主库；确认 checkpoint 成功或给出错误，不得静默。

此剧本不过，M1 不得发布。
